# ADR 0015: Sync — a node bridges to the person's home say

Status: proposed (2026-10-26)

## Context

An embedded node is its own instance (ADR 0013): its rooms, log and
principals live in the app's SQLite and nowhere else. A person who runs
say on a server, in the TUI on a laptop and in an app on a phone has
three unrelated instances. They want one chat on all of them, and they
want each device to work offline: read what it has, write, and catch up
when the network is back.

This ADR covers one person's devices and one server. Federation between
the servers of different people (Matrix style) is a different problem and
is not designed here.

ADR 0014's bridges already do most of what a device needs. An account
bridge is a person's own account somewhere else; each remote chat becomes
a portal, the people there are ghosts, the owner's messages go out as
them, and the owner's messages from other clients come in as the owner.
Delivery reads the room log from a cursor per link, incoming messages are
taken exactly once, and the bridge's state shows in the room. What it
lacks for sync: messages are text only, an offline bridge expires sends
after ten minutes, and a send with an uncertain outcome is never retried.

## Decision

- **Hub and spoke.** One say is the person's **home**: a server, or any
  node others can reach. Devices sync with home, never with each other.
  Home's log is the truth; a device holds a replica of the person's part
  of it, plus anything it keeps local.
- **Sync is a bridge.** A network `say` in `account` mode
  (`internal/bridge/say`) connects a node to home as the node's local
  user. Each home room the person is in becomes a portal on the device;
  each other home principal (person, agent, ghost) is a ghost there; the
  person's messages from the web, the TUI or another device come in as
  the local user (`Author.Self`). It runs on the bridge runner, lease,
  cursors, delivery rows and Accounts page that exist, so a device shows
  home as one more account, live or offline.
- **The protocol, not the store.** The network is a client of home's
  REST and `/ws` API (`protocol/`), with the token below. It follows every
  room with stored cursors and rereads `GET /rooms` on each `rooms` push,
  as a bot session does. Package `say` imports the bridge networks, so the
  network cannot import `say.Client`; the client moves to an internal
  package that both use.
- **A device token, not a session.** Pairing asks for home's URL and the
  username on the Accounts page, then the password through a prompt
  (`Host.Ask`). A new `POST /api/v1/devices` takes the username, password
  and a device name and returns a token that does not expire, named
  `device:<name>`, which replaces an earlier one of the same name (as
  `LocalUser` does). The token is kept in the bridge's state, never its
  settings, and the password is not kept. Revoking it unpairs the device;
  listing devices comes with token management.
- **Messages keep their parts.** `Incoming` and `Outgoing` gain `Parts`,
  which a network may fill instead of `Text`. The say network carries
  parts, causation and edits as home logs them, and reactions once say
  has them. An attachment part keeps home's file reference, and the
  device fetches the file from home when it is opened.
- **Idempotent networks retry.** A network may declare its sends
  idempotent. The say network sends with the idempotency key
  `sync:<device id>:<event id>`, so home takes a repeat as the same
  message. For such networks a send that failed for an unknown reason,
  or a `sending` row left by a stopped node, is retried with backoff
  instead of turning `unknown`. Sends do not expire either: a message
  written offline goes out whenever home is back, in log order. ADR
  0014's rules stay for every other network.
- **Home orders, the device shows arrival.** Home gives a message its
  `seq` and time when it gets there. A device's log is in the order
  events reached it, so a message written offline sits above what others
  wrote meanwhile until the device catches up, and stays there. Messages
  show home's time once home has them. Rewriting a device log into home's
  order would break every cursor on the device, and the difference is in
  one person's view only.
- **Edits converge on home.** A device applies every edit home logs, its
  own echoes included, in home's order. Two devices that edit the same
  message offline both end on the edit home took last. Messages are
  matched by remote id, so the device's own messages are never taken in
  twice.
- **What stays local.** Rooms on the device that are not portals stay on
  the device. In a portal, only the person's own messages go to home
  (ADR 0014): a device's built-in agent or bot may answer there, and its
  messages stay on the device. Home's agents answer on home and reach the
  device as ghosts; no agent runs twice. Typing and streaming frames are
  not synced, only the final message.
- **Network bridges stay on home.** A Telegram or Slack account belongs
  on home, which is up; its portals reach every device as home rooms, and
  a message written on the phone goes out through home's bridge. A device
  may still hold an account of its own (a Signal link on the laptop), and
  those portals stay on the device.
- **Backfill is recent.** A new pairing fetches each room's events from
  the last 30 days, at most 500 per room; older history is read from home
  when the person scrolls back to it, and is not kept.

### Phases

1. Pairing, portals for home rooms, messages and edits both ways,
   idempotent retries without expiry, backfill.
2. Attachments, reactions, receipts and unread counts shared between devices, home's
   delivery states on the device (sent to Telegram, failed), and room
   names and member lists kept in step instead of ghosts joining when they
   first speak.
3. Rooms made on a device: created on home on the next sync, with the
   members the device can name (home principals only), linked in one
   transaction as portals are.

## Alternatives

- **Replicating the database** (SQLite sessions, Litestream, CRDTs): each
  instance allocates its own `seq` and ids, and the log's guarantees
  (gapless `seq`, idempotency per room, causation chains) do not survive
  two writers. Permissions would have to be enforced by every replica.
- **Devices as thin clients with a cache**: simpler, but ADR 0013 runs the
  whole core in the app so that local agents, bots and bridges work with
  no server. A cache would have to grow into a node anyway.
- **Federation between equal servers**: right for many people's servers,
  far more than one person's devices need, and it can come later as its
  own connector without changing this one.
- **Device to device sync**: no device is always up, and phones cannot
  accept connections.

## Consequences

- No second sync protocol: home sees a device as one more client of the
  public API, and the device sees home as one more account.
- A device's room order can differ from home's after offline writes.
  Search, cursors and agents on the device use the device's order.
- Home people are ghosts on the device, so a person's identity there is a
  bridge ghost, with its network badge, not a principal of the device.
- A phone syncs only while the app runs (ADR 0013); background fetch and
  push wake-ups are platform work for later.
- Home holds every device's sent messages, so a device is only as private
  as home. Nothing is end-to-end encrypted.
